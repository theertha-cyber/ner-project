1. Cold Open — Why This App Exists

Read this first. Everything else in the app is in service of the idea below.

The problem

Off-the-shelf Named Entity Recognition (NER) models are trained to find generic things — person names, organizations, locations. A recruiting company wants a resume parser that pulls out YEARS_OF_EXP, PROGRAMMING_LANGUAGE, and DEGREE. A legal team wants CLAUSE_TYPE out of contracts. A generic model can't do that out of the box — and normally, getting a custom model means standing up your own ML team, your own training pipeline, and your own serving infrastructure.

Why it exists

This platform is that missing piece. It's a self-serve product: a company ("tenant") signs up, defines its own entity schema, uploads documents, gets them labeled by its own reviewers, clicks "train", and ends up with a private fine-tuned model serving its extraction requests — plus a chat assistant to ask natural-language questions about the results. No ML team required on the tenant's side.

Who uses it

Four roles, each with a distinct job in the lifecycle:

🛡️ System AdminPlatform operator. Manages tenants, sets quotas, approves/rejects training jobs before GPU time is spent.
🏢 Tenant AdminA customer's admin. Defines entity types, uploads documents, assigns annotation work, submits training jobs, promotes models.
✍️ AnnotatorLabels the training data — the human in the loop that makes fine-tuning possible.
👤 Business UserDay-to-day consumer. Uploads documents, runs extraction, reviews results, chats with the AI assistant.

2. Initial Requirements

Original problem statement

Build a multi-tenant document intelligence platform where each tenant can define domain-specific named entities, train a tenant-specific NER model, deploy that model in an isolated runtime, and use the extracted structured data for workflows, reporting, and agentic (chat) conversations.

Key requirements gathered

  • Multi-tenant from day one, with hard data isolation between tenants — not just a shared table with a tenant_id column.
  • No "bring your own model" — every tenant fine-tunes from one curated base model, so the training pipeline stays uniform and supportable.
  • Training must be human-gated: a System Admin approves each job before GPU resources are spent, and a tenant can't even submit until it has enough labeled data.
  • The delivery process itself was a requirement — every feature must go through spec-driven development with agent-assisted implementation under human approval, not "just start coding."

Constraints & assumptions

  • Small team (1-3 people), greenfield project — the architecture favors "good enough for one team to operate" over hyperscale from day one.
  • The local/dev environment intentionally substitutes lighter infrastructure for what's targeted in production (e.g. MinIO instead of S3). See Gaps & Rework for exactly where dev and the documented target architecture diverge.
  • Secrets must never have code-level defaults — the app is required to fail at startup rather than silently run with a default JWT secret or storage password.

3. Planning & Approach

How requirements were broken down

Large features are run through a "feature decomposer" step that splits a requirement into numbered submodules (SM-01, SM-02, …). Each submodule becomes its own OpenSpec change with a full lifecycle: proposal → design → spec → tasks → evidence → archive. You can see the paper trail in openspec/specs/ (60+ durable capability specs) and openspec/changes/ (work currently in flight).

Design decisions worth knowing before you touch anything

ADR-001 — Tenant isolation via separate DB schemas▸

Each tenant gets its own PostgreSQL schema (tenant_<id>), not a shared table with a tenant_id filter, and not a fully separate database. Stronger blast-radius containment than row-level security, cheaper to operate than database-per-tenant. Trade-off: every tenant schema must be migrated in lockstep.

ADR-002 — Single base model, no BYOM▸

Every fine-tune starts from dslim/bert-base-NER. This massively simplifies the training worker (one tokenizer, one label scheme to map from) at the cost of tenants not being able to bring exotic base models.

ADR-003 — Per-tenant model serving topology▸

Today: a shared serving pool with tenant-aware routing, version pinning, and on-demand model loading. Documented future path: dedicated serving pods for large tenants.

ADR-004 — OpenSpec spec-driven development governance▸

Mandatory gates for any non-trivial change: proposal → design → spec → tasks → evidence → archive. Exceptions exist only for trivial changes.

ADR-005 — OpenCode agent permissions and boundaries▸

Role-specific AI agents with bounded tool access, human approval gates, and audit logging of agent actions — an agent doing a database migration doesn't also get blanket permission to touch production secrets.

ADR-006 — Async GPU training workers▸

Celery-based workers, designed to scale-to-zero with checkpoint-based resume on GPU node pools.

ADR-007 — Chatbot architecture with full RAG and guardrails▸

Three-source retrieval-augmented generation: SQL + pgvector (semantic search) + NER extraction results. A SQL validation layer and mandatory source citation are part of the design, not an afterthought.

Worth knowing All seven ADRs above are currently marked "Proposed" in docs/adr/, not "Accepted." They document real decisions being followed in practice, but haven't been formally ratified — don't treat them as immutable without checking their current status.

5. Architecture Overview

The system is a set of independently-deployable FastAPI services behind a gateway, sharing one PostgreSQL instance (tenant-isolated at the schema level), with MinIO for object storage, Redis for caching + Celery queues, and MLflow for experiment tracking / model registry.

Data flow — the "hot path" (extraction, using an already-trained model)

  1. Business user uploads a document → gateway → document_service validates it, runs OCR, stores the file in MinIO, and persists text spans.
  2. Extraction is triggered → extraction_service enqueues a Celery task on the extraction queue.
  3. celery_worker_extraction picks it up and calls model_serving's internal inference endpoint for that tenant.
  4. model_serving resolves the tenant's active (promoted) model version + label list, loads the ONNX model into its in-memory cache if not already warm, and runs inference.
  5. extraction_service post-processes the predictions into entities and persists them to extracted_entities.
  6. The business user reviews/confirms entities in the portal, then can ask the chat assistant about them (chat_api → rag_orchestrator → SQL + pgvector + model_serving).

Data flow — the "cold path" (training, run once per model version)

  1. Tenant admin submits a training job (requires 500+ confirmed spans) → training_service.
  2. System admin approves the job — this is the GPU-spend gate.
  3. celery_worker fine-tunes dslim/bert-base-NER on the tenant's BIO-tagged export, logs metrics + artifacts to MLflow, and exports an ONNX version.
  4. Tenant admin reviews metrics in the portal and promotes a version → model_serving is warmed up with it.

9. Bugs & Issues

Open

Training-quality bug: eval F1/precision/recall = 0.0 on model v8Open · High

Every entity class scores exactly 0.0 on eval despite the eval set containing plenty of positive examples (e.g. 308 CONTACT_DETAILS, 84 TOOL_FRAMEWORK examples). Confirmed this is not a routing/loading bug — the pipeline correctly loads and serves this model version. It just doesn't predict anything correctly.

Suspected causes to check first: token/label alignment in the training worker's label_all_tokens=True strategy, a bug in the metrics computation, or the model simply being undertrained (1 epoch, ~162 samples) in a way that masks a real alignment bug.

Status: investigation was paused by the previous owner — pick this up before trusting any tenant's live model quality numbers.

Fixed (six chained bugs, same symptom: extraction silently used the base model)

See all six — each was masked by the same graceful-degradation fallback▸
  1. S3 artifact path mismatch between the training worker and the model loader.
  2. label_list never persisted to model_versions.metrics.
  3. Hardcoded port — model_serving's active-version/label-list resolution pointed at the host-mapped training_service:8003 instead of the Docker-internal :8000.
  4. Missing env var — training_service was never given NER_MODEL_SERVING_URL, so its post-training warmup call always failed silently.
  5. ONNX input mismatch — inference unconditionally sent token_type_ids, which the exported models don't declare as an input. Every fine-tuned model failed inference and silently fell back to the base model, on every single request, regardless of whether routing was correct.
  6. Timeout too tight — warmup's client-side timeout (30s) was often too short for a cold model load right after training finished; widened to 90s. Note: the server keeps loading in the background even if the client gives up, so a "failed" warmup log doesn't necessarily mean the model never loaded.
Trap to know about — MLflow vs. local DB version numbers MLflow's registered-model version number and the local Postgres model_versions.version_number column are two different sequences that can drift apart. Never assume they match when calling promote / warmup / demote by hand (curl, scripts). Always read the number from the portal UI or a live MLflow query — using the wrong one has silently promoted the wrong model version before.

10. Gaps & Rework Needed

  • Gap Every ADR in docs/adr/ is still status "Proposed", not "Accepted" — documented but not formally ratified.
  • Gap PROJECT.md's target infrastructure (RabbitMQ, HashiCorp Vault, Unleash feature flags, PgBouncer, Kubernetes/Terraform) is largely aspirational for local dev. What actually runs via docker-compose.yml is Redis+Celery (not RabbitMQ) and plain .env files (not Vault) — don't assume the tech-stack table in PROJECT.md describes what's running when you docker compose up.
  • Rework Graceful-degradation fallback code in the serving path repeatedly masked real failures during the bug hunt above — every one of the six bugs fell back to the base model silently instead of surfacing an error. Worth auditing anywhere inference or model resolution swallows an exception and falls back quietly; it's a debugging trap waiting to happen again.
  • Rework The 500+ confirmed span training floor and the single-epoch default training config are both worth revisiting once the v8 quality bug (see Bugs) is understood — right now, an undertrained model and a genuinely broken one look identical from the outside.

13. Developer Onboarding Notes

How to run the project

  1. Read AGENTS.md first — it's short and tells you which docs/ file to read next for whatever you're about to do. Then read PROJECT.md for full project context.
  2. Set up a local .env file — the app has no secret defaults on purpose and will refuse to start without one.
  3. Run docker compose up — this brings up Postgres+pgvector, MinIO, Redis, MLflow, all 8 backend services, and 2 Celery workers. The db-init service runs Alembic migrations and seeds data before anything else starts.
  4. Run the portal frontend separately from src/portal/ (Next.js dev server) — it is not containerized in docker-compose.yml.
  5. Tests live under tests/unit, tests/integration, tests/contract at the repo root, plus some service-local folders (e.g. src/chat_api/tests/, src/document_service/tests/).

Key things to know before modifying anything

  • This project is spec-driven. Before writing code, find or create the relevant OpenSpec change — don't skip straight to implementation, even for "small" changes. See Concepts below.
  • Conflict resolution order when instructions disagree: ADR > PROJECT.md > AGENTS.md > docs/.
  • When in doubt, escalate to a human rather than assume — the guardrails doc (docs/agents/guardrails.md) lists explicit escalation triggers.

14. Concepts Used

Three terms you'll see constantly in this repo. Beginner-friendly explanations below.

📐

SDD

Software / Spec-Driven Development

What it is: a way of working where you write down what you're building and how, in a reviewable document, before you write the implementation — the opposite of "just start coding and figure out the design as you go."

Why used: with AI agents doing a lot of the implementation, an unambiguous, human-reviewed spec is what keeps agent output aligned with what was actually decided, instead of the agent guessing.

How it helped here: every capability in this repo has a durable spec under openspec/specs/. It's a hard rule (AGENTS.md invariant #1): no code before a reviewed spec exists.

📂

OpenSpec

The specific toolset used for SDD here

What it is: a folder convention plus a lifecycle. openspec/specs/ holds durable "this is how it works today" documents; openspec/changes/ holds proposed changes moving through proposal → design → spec → tasks → evidence → archive.

Why used: gives every change a paper trail — why a decision was made (design.md), what was promised (spec.md), what was actually done (tasks.md), and proof it works (verification.md) — without digging through chat history.

How it helped here: openspec/changes/ currently shows real in-flight work you can read end-to-end to understand exactly what's being built and why, before it's ever merged.

🤖

OpenCode

Agentic engineering interface

What it is: the tooling (.opencode/agents, .opencode/skills, .opencode/commands) used for planning, implementing, reviewing, and validating changes with AI agents, under human approval gates. A legacy .claude/ folder exists while the project migrates.

Why used: ADR-005 defines role-specific agents with bounded tool access, so an agent doing one kind of task doesn't automatically get permission for unrelated, riskier actions.

How it helped here: the SDD pipeline isn't just paperwork — it's the actual contract agents work against. An agent implementing a task reads the real spec.md/tasks.md, and its output is checked against verification.md before a change is archived.

15. Summary — Recap & Next Steps

This is a multi-tenant platform that turns "we have documents with domain-specific information in them" into "we have a private extraction model and a chat assistant over our own data" — gated by human approval at the training and promotion steps, and built under a spec-first, agent-assisted process (OpenSpec + OpenCode).

What a new developer should do next

  1. Get the stack running locally (see Onboarding) and log in as each of the four roles once, so the workflow section stops being theoretical.
  2. Read openspec/specs/model-serving and openspec/specs/training-worker first — that's where most of the real bugs have lived.
  3. Before your first change, find or write the OpenSpec change package for it — don't skip the spec step even for "small" changes.
  4. Ask about the open model v8 training-quality bug before trusting any tenant's live model numbers.
