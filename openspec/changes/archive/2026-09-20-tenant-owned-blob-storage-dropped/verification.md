## 2. Hallucination Risk Register

| # | Risk Area | Potential AI Error | Human Check Required |
|---|-----------|-------------------|----------------------|
| 1 | Fallback to platform storage (design Decision 4) | The single most damaging error in this change. An agent writing defensive code may add a `try tenant container / except: write to MinIO` path, or a retry that resolves the store afresh and lands on the platform default, because falling back reads as robustness. The result writes tenant content to platform infrastructure permanently and silently, which is the one outcome the change exists to prevent. | Read every `except`, retry decorator, and `or get_durable_store()`-shaped default on the write path. Confirm no code path reaches a platform store after a tenant store was resolved. Run the "There is no fallback write" scenario against an instrumented platform store and assert zero puts. Grep for a default argument or `None`-coalescing that could silently substitute the platform instance. |
| 2 | Read/delete routing source (design Decision 2) | An agent may resolve the store for `open` and `delete` the same way it resolves it for `put` — from the tenant's current profile — because that is the symmetric-looking implementation. This compiles, passes single-backend tests, and breaks only for a tenant that has switched backends, where it silently reports existing content as missing. | Confirm `open` and `delete` take the recorded kind as input and never consult the profile, the resolver, or the data-plane record. Verify by test: store a document, activate a connection, re-open the document, assert the bytes are returned. Grep the read path for any call to the profile or connection lookup. |
| 3 | Backfill and NULL handling (design Migration step 1) | An agent may default the new column in a way that treats a missing value as "resolve it now" rather than as the platform kind, or may treat the legitimately absent kind on a `source_only` document as an error and fail ingestion for those tenants. | Inspect the migration for a backfill that sets every existing non-NULL-reference row to the platform kind. Confirm `source_only` documents and post-deletion `ephemeral` documents pass through the read path without raising. Check the column default applies to rows written by code paths not touched in this change. |
| 4 | Working-copy prefix and lifecycle rule (design Decision 3) | An agent may write working copies under the durable prefix, or invent a prefix name that does not match what the connection test asserts a lifecycle rule against. Both leave `ephemeral` bytes with no expiry — retention silently stops being a guarantee while every test still passes. | Confirm one constant defines the working prefix and that both the adapter's key construction and the connection test's lifecycle assertion read that same constant. Store an `ephemeral` document against a real container and confirm the object lands under the prefix the rule covers. |
| 5 | Provider separation (design Decision 1) | An agent may extend the existing `azure_blob` provider rather than adding a fourth, or may reuse its validation, secret kind, or resolver mapping — the two look near-identical in configuration shape. This grants write privileges to a connection the tenant approved as read-only, and breaks the one-active-per-provider guarantee. | Confirm `azure_blob_content_store` is a distinct member of `PROVIDERS` with its own secret kind, config validation, and test suite. Confirm the resolver maps `("content_store_adapter", "tenant_azure_blob")` to the content-store provider, not to `PROVIDER_AZURE_BLOB`. Verify the same-container and shared-secret rejections both fire. |
| 6 | Async/sync client boundary (design Decision 8) | The codebase already uses `azure.storage.blob.aio` in `blob_sync`. An agent is likely to copy that import into a synchronous `ContentStore` adapter, producing un-awaited coroutines that return truthy objects — puts appear to succeed and store nothing. | Confirm the adapter imports the synchronous `BlobServiceClient`, not the `.aio` one. Confirm no `async def` appears in the adapter's three operations. Verify a round trip returns the identical bytes rather than a coroutine. |
| 7 | Scope of the retention relaxation (design Decision 5) | An agent may lift `RetentionModeNotPermittedForDataPlane` unconditionally, or widen `SYNC_ALLOWED_RETENTION` to include `platform_blob` for all tenants, because the change is described as "lifting the restriction". Either permits durable platform-side storage for a residency tenant. | Confirm both relaxations are conditional on the tenant's content-store selection being executable, not on the data-plane mode alone. Run the "Platform blob retention is rejected for a residency tenant without a content store" and "Platform-stored durable retention still blocks a sync" scenarios and assert both still fail closed. |
| 8 | Cache invalidation (design Decision 4) | An agent may cache resolved stores keyed by tenant with no invalidation hook, so a retired or rotated connection keeps serving from a cached client built on a credential that is no longer active. | Confirm pause, retire, and replace each invalidate the tenant's cache entry. Test: activate, write, retire, write again — the second write must reach the platform store, not the cached tenant client. Confirm the cache is bounded. |
