## 2. Hallucination Risk Register

| # | Risk Area | Potential AI Error | Human Check Required |
|---|-----------|-------------------|----------------------|
| 1 | Snapshot source (design Decision 2) | The obvious implementation point to persist rows from is whatever variable is already in scope where `_persist_turn_and_respond` is called — which today is closer to `admitted_evidence`/prompt-building state than raw `sql_results`. An agent could wire the snapshot to `AdmittedEvidence.rows` instead, producing an export that is silently just as truncated as the LLM's prompt, defeating the entire point of the feature while every "export works" test still passes if it only checks that *some* rows come back. | Read the persistence code: confirm it reads `state["sql_results"]` (or an equivalent full-result variable populated by `retrieval_execution_node`), not `admitted_evidence.rows` or anything derived from `ContextAssembler._fit_rows`. Run scenario 7 specifically with a result set large enough to trigger prompt-budget truncation and assert the export row count exceeds the prompt-admitted row count. |
| 2 | Response payload scope (chat-api spec, design Goals) | An agent implementing `ChatResponse.export` might find it simpler to inline the actual row data (or a preview of it) into the field "just in case the frontend wants it," reintroducing the token/payload bloat this change exists to avoid and quietly changing the response contract beyond what the spec defines. | Read `schemas.py`'s `ChatResponse.export` type: confirm it carries only `message_id`, `row_count`, and `formats` — no row data. Inspect a live response body for scenario 9 and confirm no array of row objects is present anywhere in the JSON. |
| 3 | Export ownership check (design Decision 5, ADR-001) | The simplest implementation queries `chat_messages` by `message_id` alone and serves whatever snapshot it finds, since nothing about the row itself encodes ownership — the check has to be added deliberately by joining through `conversations`. Skipping it is invisible in the happy path (the requesting user's own messages still work) and only surfaces as a cross-tenant or cross-user data leak, which is exactly the failure ADR-001 exists to prevent. | Read the export endpoint: confirm it resolves `message_id → conversation_id → conversations.user_id/tenant_id` and compares against the authenticated request before returning any data, mirroring the existing `DELETE /conversations/{conv_id}` and `POST /messages/{message_id}/feedback` ownership checks. Run scenario 3 (non-owning user) and confirm 404, not 403 with a data leak in the error body, and not 200. |
| 4 | Export column leaking into unrelated queries (design Risks) | `export_rows` lives on the same `chat_messages` row that the existing conversation-history endpoint (`GET /conversations/{conv_id}`) already reads from — and that endpoint legitimately needs the small `export_row_count` integer (scenario 15, so a file card survives a reload). An agent extending that shared query could easily select the bulky `export_rows` JSONB column too, "since it's right there," quietly reintroducing the payload-bloat problem this change is meant to avoid. | Diff the `GET /conversations/{conv_id}` query/model: confirm `export_row_count` IS selected (required for scenario 15) but `export_rows` is NOT. Load a conversation with a large snapshot and confirm the conversation-history response size does not grow proportionally to the snapshot size. |
| 5 | CSV/XLSX formula injection (design Decision 4, external dependency) | Row values ultimately originate from extracted document/entity data (e.g. a candidate's name, organization, or skill text pulled from an uploaded resume), which is attacker- or third-party-authored content the platform does not control. A naive CSV/XLSX writer passes cell values through unescaped; a value beginning with `=`, `+`, `-`, or `@` is interpreted as a formula by Excel/Sheets on open, a known CSV-injection vector (OWASP). | Confirm the CSV/XLSX renderer neutralizes leading `=`, `+`, `-`, `@` characters in cell values (e.g. prefixing with a `'` or a space) before writing. Construct a snapshot row containing a formula-injection payload in one field, export it in both formats, and confirm the written cell is not interpretable as a formula when opened. |
| 6 | Unbounded snapshot growth (design Risks, ADR-014 Negative consequence) | The snapshot's size safety rests entirely on the SQL generator's current 1000-row cap, which this change does not itself enforce — it's an assumption borrowed from `sql_generator.py`. An agent implementing the persistence step could write the snapshot without re-checking that assumption, so a later unrelated change to `sql_generator.py`'s `LIMIT` clamp would silently remove this feature's only size guarantee. | Confirm the persistence code either re-clamps snapshot row count defensively or has an explicit comment/test tying it to `sql_generator.py`'s `DEFAULT_LIMIT`/1000-row clamp, so a future change to that constant is forced to consider this feature. Add a regression test asserting a snapshot never exceeds 1000 rows even if `sql_results` somehow contained more. |
| 7 | Migration pattern deviation (design Migration Plan) | The design specifies the exact per-tenant-schema `DO $$ ... FOR schema_name IN SELECT nspname FROM pg_namespace WHERE nspname LIKE 'tenant\_%'` loop pattern from `010_chatbot_infrastructure.py`. An agent could instead write a single `ALTER TABLE tenant_template.chat_messages ...` and forget the loop, which would pass any test run against a freshly-provisioned test tenant (which inherits from `tenant_template`) while silently leaving every already-provisioned tenant schema without the new columns. | Diff the new migration against `010_chatbot_infrastructure.py`'s loop structure and confirm both `tenant_template` and the `tenant_%` loop are present in `upgrade()`, with a matching `downgrade()`. Run the migration against a test database seeded with at least one non-template tenant schema and confirm `export_rows`/`export_row_count` exist in both. |
| 8 | Truncation gated on line count instead of result count (design Decision 3, revision 3) — **materialized live** | The obvious implementation reads "preview the first N lines" literally and gates truncation purely on how many lines the rendered reply has (`lines.length > PREVIEW_LINE_LIMIT`). This passes every test that only exercises "list many things" style questions, but a detailed answer about a *single* result (job title, experience, education, each on its own line) has just as many lines as a real list — an agent implementing this naively ships a card that reads "See more (12 more)" under a one-result answer, which is exactly what shipped here before a live query caught it. | Read the truncation condition in `MessageThread.tsx`: confirm it requires **both** `export.row_count > PREVIEW_LINE_LIMIT` **and** `lines.length > PREVIEW_LINE_LIMIT`, not line count alone. Run scenario 18 (`export.row_count = 1`, 8-line reply) and confirm the full reply renders with no file card and no "See more". |
| 9 | Empty structured result treated as a real snapshot (design Decision 2 refinement) — **materialized live** | `sql_results is not None` reads naturally as "structured retrieval succeeded," but a query that validates and executes cleanly against zero matching rows (e.g. the LLM targeted an empty or wrongly-named entity relation) also satisfies that check. An agent persisting on this condition ships a "0 results / Download the full result" card with nothing useful behind it — observed live against a tenant with a populated `NAME` entity type and an empty, similarly-named `full_name` entity type. | Read the persistence condition in `_persist_turn_and_respond`: confirm it is `if sql_results:` (truthy — a non-empty list), not `is not None`. Run scenario 16 (`sql_results = []`) and confirm no snapshot is created and `export` is omitted from the response, identical to structured retrieval never having run. |

ADD COLUMN`, not `CREATE TABLE`.
